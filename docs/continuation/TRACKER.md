## Release 3.12.3 (2026-10-29)
Smoother, and current on its own. The interface no longer recomposites the whole screen behind the photo on every keystroke and every streamed token: it lays again only the rows whose text changed, and a burst of stream chunks is drawn once rather than a frame per character — a typing frame dropped from 18 ms to under half a millisecond, with the picture unchanged to the pixel (WS-56). ## WS-56: Smoothness — the interface should not feel laggy (2026-10-29)
User: "optimize the speed of Friday, it should be smooth to use and not feel laggy." Profiled the render hot path. Two costs stood out, both paid on every keystroke and every streamed token. First, streaming rendered one whole frame per chunk: the forwarder sent one message per `acp` chunk, so a fast reply was a frame per character. Now a burst is coalesced — the forwarder drains whatever has already arrived and delivers it as one `agentBatch`, one render per drain, nothing held back. Second, and larger: the wallpaper recomposited the entire screen through the lipgloss/ultraviolet canvas on every changed frame (~18 ms, ~48k allocations, measured), capping the frame rate while a photo is on. It now caches each composited row positionally and lays again only the rows whose text changed — a keystroke or a streaming line touches a handful of rows, not the whole screen. A typing frame went from 17.98 ms to 0.455 ms (~40×) and from 48,802 allocations to 531, with byte-identical output (the wallpaper suite — every cell, every screen and size, never a changed word, every glyph on glass — still passes). The fixed per-cell photo maths are also worked out once per grid rather than per frame.

## Release 3.12.2 (2026-10-29)
Long tasks run smooth on every provider. This release makes the limits that keep tool running fast into one measured, checked invariant: a step's tool results always fit what compaction keeps, a reply can never overrun the window, and the conversation is trimmed before a slow turn goes out, not after. A big tool result is no longer lost to truncation — its full output is saved under the project and the model reads it back by path when it needs the part left out. And nothing can quietly stall a turn: every model stream is held to an idle limit and every command the model runs takes a deadline, both enforced by static checks that fail the build if a future change routes around them. Splitting work across sub-agents, which keeps each context small, was already there (WS-53, WS-54).

## WS-54: The flow invariant — a step's results fit what compaction keeps (2026-10-29)
User: "ensure continuous tool running using all providers, the tool commands shouldn't stall or send too many tokens as context, create an architecture using invariants and static analysis to create something truly smooth." Found: nothing tied the per-call bounds to the window, so one step could return `MaxToolCallsPerStep × MaxResultChars` = 16 × 40,000 = 640,000 characters (~160k tokens) — larger than the 128k window and five times what compaction keeps verbatim, so a fat step overflowed before compaction could act and then had its just-fetched results summarized away. The fix is one measured invariant chain, held by a conformance test: a step's results (`S`) ≤ what compaction keeps verbatim (`K = window/4`) ≤ the compaction trip point (`C = 0.8·window`) ≤ the window (`W`). A per-step budget (`StepResultCharsFor` = window/2 characters, half of `K` for margin, scaling with `ARCHYMEDES_CONTEXT_LIMIT`) is shared max-min fair across the step's calls — small results pass whole, large ones are trimmed to an equal ceiling and told to spread work over steps. Output headroom is reserved so a reply never overruns the window (`C + reply ≤ W`). Liveness is made provider-agnostic by holding every model stream to the idle watchdog — the summariser/title/`/btw` `complete()` path as well as the main loop — enforced by a static call-site check (`model.Stream` is reachable only from the two guarded helpers). A study of how Codex (`codex-rs`) and Claude Code (`query-engine.ts`) run long tasks confirmed the shape (compact before each call, a hot tail kept verbatim, per-call result budgeting, headroom reservation) and pointed to result-offloading as the next gain (WS-54.3). Splitting work across sub-agents to keep each context small already exists (`delegate_task`/`delegate_readonly_task`, `background` + `wait_agents`, roles, worktrees); no new mechanism needed.

## Release 3.12.1 (2026-10-28)
A fix for long runs that appeared to freeze. In auto mode, where Friday can work for a long stretch without you saying anything, the conversation stopped being compacted: it kept everything since your last message word for word, and in a long run that was the whole thing, so every turn carried millions of tokens and took minutes before you cancelled it. Compaction now keeps the most recent quarter of the context window verbatim and summarizes the rest, even when there is no recent message of yours to anchor on, and it checks the size before each turn as well as after, so a conversation already over the line is trimmed before the slow turn goes out rather than after it (WS-53).

## WS-53: Compaction trims the tail on a long auto run (2026-10-28)
User: "friday stalls when a command in auto mode" — turns of 320 s carrying 2.0M input tokens, cancelled and resumed. Compaction fires at 80% of the window but never shrank: it kept everything after the last message the person sent verbatim, and in auto mode that message is the first one, so the tail was the whole run. Once the summary was prepended to that first message it sat at index 0 and `cut <= 0` made every later compaction bail silently, so the conversation grew without bound and each turn's request got slower until it looked frozen. The cut is now `max(last user message, recent-budget cut)`: the most recent quarter of the window is kept word for word on a step boundary (never splitting a tool call from its result) and everything older is summarized, even when there is no human turn to anchor on; a deep cut that lands on an assistant step carries the summary as its own user message so the conversation still opens with the person.
